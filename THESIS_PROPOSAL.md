I am writing to formally request your supervision of my BSc thesis and to propose **HeiwaseWeb** — the public website and, going forward, the content-management platform of *Heiwase Karate Szeged*, a real, currently operating local sports club — as its subject.

This is a self-contained, end-to-end distributed-systems and secure-software-engineering problem, bounded enough to fit a BSc thesis timeline, yet deep enough to justify one — and it ships to real users at the end of it.

I am asking you to supervise this thesis because it offers exactly the combination a strong BSc thesis needs: an authentic external client and problem (not an artificial toy project), a codebase that already demonstrates engineering maturity (documented below), a precisely scoped and prioritized backlog that can be mapped directly onto thesis milestones, and a set of genuinely non-trivial technical problems — REST-based data access without an SDK, client-side authentication security, untrusted-content rendering, multi-module architecture, and performance/testing discipline — that map cleanly onto core software engineering curricula (software architecture, secure systems, distributed/serverless computing, and empirical software engineering).

## 2. Problem Statement & Objectives

### 2.1 The Real-World Problem

Local, volunteer-run sports clubs such as Heiwase Karate Szeged need a professional public web presence but typically have neither the budget for commercial CMS hosting and plugin licensing (e.g., managed WordPress) nor in-house engineering staff to maintain one. In the current system, this problem has only been half-solved: the site itself is fast, polished, and bilingual, but **all of its content is compiled into the application**. Every section of the homepage (`Heiwase.App.Blazor/Components/Pages/Home/Home.razor`) is a hard-coded Razor component; the Hall-of-Fame roster is a static JSON file shipped inside `wwwroot/data/`; and each piece of localized copy exists as a *duplicated, hand-authored Razor partial* per language (e.g. `AboutSection_hu-HU.razor` and `AboutSection_en-US.razor`, selected at render time by `CultureInfo.CurrentCulture`). Consequently, publishing a single news item, updating a result, or correcting a typo in club information requires a developer to edit source code, rebuild, and redeploy the entire WebAssembly bundle. There is no way for a non-technical club administrator to author or publish content independently, and there is no persistence layer at all — the "database" is literally version-controlled JSON.

### 2.2 Primary Objectives

1. **Preserve and not regress** the existing fast, accessible, bilingual public landing experience that already serves real visitors.
2. **Decouple content from code** by introducing a real content-management capability: a secured admin application through which non-technical staff can author, edit, and publish rich-text news articles without any code change or redeployment.
3. **Introduce a persistent, serverless, $0-tier backend** (Firebase Firestore for structured data, Firebase Storage for media blobs) accessed exclusively through hand-built REST integrations, since no first-party Firebase SDK targets Blazor WebAssembly.
4. **Re-architect the single-project solution into a layered, multi-module system** — a public site, a separately deployable admin dashboard, a shared model/contract library, and an infrastructure library encapsulating all external I/O — enforcing separation of concerns across two independently deployable WebAssembly front-ends.
5. **Harden the resulting system**: authenticate administrators (Firebase Authentication, JWT-based sessions), author least-privilege Firestore/Storage security rules, and safely convert untrusted, administrator-authored Markdown into HTML that is rendered on a public page.
6. **Automate delivery** via CI/CD so that both the public site and the admin dashboard are independently built and deployed (e.g., to separate Netlify targets) on every change.

### 2.3 Academic & Practical Relevance

Academically, the objectives above span several core software-engineering research areas simultaneously: **serverless/distributed systems architecture** (designing a client that talks to a Backend-as-a-Service purely through its REST surface, including document mapping, querying, and error/retry semantics that an official SDK would normally hide); **applied security engineering** (authentication/session handling in a public WebAssembly client, declarative authorization via security rules, and defense against injection when rendering user-authored Markdown as HTML); **software architecture** (migrating a monolithic client to a modular, layered system without introducing circular dependencies or duplicated logic); and **empirical software engineering** (introducing automated testing and performance benchmarking into a codebase that currently has neither). Practically, the outcome is not a simulation: it is a system that a real club will use to publish real news to real members, giving the thesis immediate, demonstrable, external validity in addition to its academic contribution.

## 3. Current Implementation Status

### Architecture & Tech Stack

The repository currently ships a **single-project solution** (`Heiwase.App.slnx` → `Heiwase.App.Blazor/Heiwase.App.Blazor.csproj`), a **Blazor WebAssembly Standalone** application targeting **.NET 10** (`net10.0`, nullable reference types and implicit usings enabled), deployed as a purely static, client-only bundle — there is no server-rendered host, no API project, and no database. It is hosted on Netlify at `https://szegedkarate.netlify.app/` today.

- **UI framework & component model.** Feature areas are organized under `Components/Layout`, `Components/Pages`, and `Components/Shared`, each following a strict one-type-per-file, code-behind pattern (`Foo.razor` for markup, `Foo.razor.cs` for logic as a `partial class`, `Foo.razor.css`/`.less` for styling). This convention is not incidental: it is the codified result of issue **#2 "Refactor code structure"** ("Every class, enum or other type should have its own file… follow SOLID principles… No inline CSS allowed… JavaScript… injected via Blazor"), delivered through PRs **#12** and **#13**. The presence of an explicit, issue-tracked *refactor-for-maintainability* milestone this early in the project's life is itself evidence of engineering discipline worth building on.
- **Component library.** **Radzen.Blazor 11.2.5** supplies the `DialogService`/`RadzenComponents` used for all 16 modal dialogs, themed via `RadzenTheme Theme="material"` in `MainLayout.razor`. A single static factory, `Components/Shared/DialogDefaults.cs`, centralizes dialog chrome (size, overlay behavior, close/drag/resize behavior) so every modal in the app shares one consistent frame — a small but genuine application of the DRY/single-source-of-configuration principle.
- **Design system.** All component styling is authored in **LESS** and compiled to scoped `.razor.css` at build time via `dotless.Core 1.6.7`, orchestrated by `compilerconfig.json` across 14 input/output pairs. A shared token file, `wwwroot/css/_variables.less`, defines the entire visual language as reusable variables and mixins (colors, breakpoints, gradients, and mixins such as `.reveal-on-visible()` for scroll animations and `.responsive-bg(@name, @folder, @ext)` for format-negotiated background images) — a lightweight but real design-token architecture.
- **Internationalization.** The UI is fully bilingual (Hungarian/English) through two cooperating mechanisms: (1) `Microsoft.Extensions.Localization 9.0.1` with 9 `.resx` resource sets (`IStringLocalizer<T>` injected per component) for interactive chrome — navigation labels, buttons, and, notably, resource-driven `[Required]`/`[EmailAddress]` validation messages; and (2) a **culture-forked content pattern**, where every page section is a thin shell (e.g. `AboutSection.razor`) that renders either a `_hu-HU` or `_en-US` fully-authored sub-component based on `CultureInfo.CurrentCulture.Name`. The user's language choice is persisted in `localStorage` under the `blazorCulture` key and re-applied during WASM bootstrap in `Program.cs` *before* the root component renders, with `BlazorWebAssemblyLoadAllGlobalizationData` enabled for full ICU support. This hybrid approach works well at the current content volume but, as discussed in Section 4, does not scale to database-authored content — a direct architectural link to the planned CMS work.
- **Client-side interactivity & JS interop.** A single ES module, `wwwroot/js/animations.js`, is loaded through `IJSObjectReference` and provides two independent capabilities: an `IntersectionObserver`-based scroll-reveal effect for `.feature-card`/`.info-bubble`/`.feature-item` elements, and a hand-built, promise-aware CSS-transform carousel engine (`initTrack`/`slideTrackLeft`/`slideTrackRight`/`resetTrack`) that drives the auto-advancing Hall-of-Fame competitor/senpai sliders in `HallOfFameSection.razor.cs`, including pause-on-interaction and timed auto-resume logic (`System.Timers.Timer`). No inline `<script>` blocks or direct DOM manipulation from C# are used — all interop crosses a clean, explicit JS-module boundary.
- **Data access today.** The only "data layer" in the application is a pair of static JSON files (`wwwroot/data/halloffame.json`, `hallOfFameEn.json`) fetched with `HttpClient.GetFromJsonAsync<HallOfFameData>()` into strongly typed `Member`/`HallOfFameData` model classes. There is no database, no API, and no server-side code anywhere in the solution.
- **Forms, validation, and third-party integration.** `ContactSection` binds a strongly typed `ApplicantModel` implementing `IValidatableObject`, combining declarative, resource-localized annotations (`[Required]`, `[EmailAddress]`) with hand-written cross-field business rules (a minor applicant must supply a guardian name; a self-defense course is restricted by declared sex; a person cannot register for mutually exclusive "child" and "adult" tracks simultaneously). Submission integrates with the third-party **Formspree** API (`HttpClient.PostAsJsonAsync` to a fixed endpoint) as a serverless "forms-as-a-service" backend, with optimistic success/error UI state — delivered under issue **#11** ("Give form backend") via PR **#19**.
- **Media performance engineering.** Every raster image is served through `<picture>` elements offering `avif → webp → jpg` fallbacks (computed via `Path.ChangeExtension` helpers on the `Member` model and the shared `.responsive-bg()` LESS mixin), and the hero background ships as `.webm` alongside `.mp4`. This was delivered deliberately and is tracked through issues **#24** ("Convert picture files… to enhance website loading performance on low connection devices") and **#26** ("Bugfix/media optimalization") — i.e., performance was already treated as a first-class, issue-tracked requirement, not an afterthought.
- **Deployment & operations today.** The build is published manually (`dotnet publish -c Release`) to Netlify. There is no `.github/workflows` CI/CD pipeline of any kind yet (confirmed by inspection — the only GitHub Actions workflow present is the dynamic one backing this very coding-agent session), and there is no automated test project anywhere in the solution. Both gaps are explicitly targeted by the backlog described in Section 4.

### Implemented Features

### Academic & Engineering Challenges

The backlog above is not a list of routine CRUD screens; each epic surfaces a genuine, non-trivial engineering problem suitable as a thesis research thread:

1. **A serverless data-access layer with no SDK to lean on.** Firebase has no official .NET/Blazor WebAssembly client. Issue #47 explicitly requires "a HTTP-based service capable of connecting to the Firestore API" — meaning the thesis must design, from first principles, a typed, testable repository abstraction over Firestore's and Storage's raw REST surfaces (document (de)serialization, query construction, pagination, and error/retry handling). This is a genuine software-architecture contribution (repository-pattern design over a schemaless REST API) and, as a side effect, a potentially reusable open-source artifact for other Blazor WASM projects facing the same SDK gap.
2. **Security-critical authentication in a public client.** Implementing Firebase email/password authentication (#43) and persisting the resulting session/JWT in `localStorage` (#44) raises concrete, well-studied client-side security trade-offs (XSS exposure of token storage, token refresh/expiry, and the blast radius of a compromised admin session) that must be explicitly reasoned about and mitigated — an applied-security case study with a defensible threat model.
3. **Declarative authorization design.** Issue #41 requires Firestore/Storage security rules that allow public, unauthenticated *reads* (so the marketing site keeps working without a login) while restricting *writes* to authenticated administrators — a compact but real distributed-authorization design problem, independent of the application code itself.
4. **Untrusted-content rendering pipeline.** Issue #58 requires converting administrator-authored Markdown into HTML with Markdig and rendering it on the public site "securely." This is a concrete injection/XSS-defense problem (allow-listing HTML output, encoding, and validating embedded image URLs generated in #50) with measurable, testable security properties.
5. **Multi-module architecture migration.** Issue #38 requires splitting one WebAssembly project into four coordinated projects (two presentation front-ends, one shared contracts library, one infrastructure library) without introducing circular references or duplicated business logic — a software-architecture exercise whose quality can be evaluated empirically (dependency-graph acyclicity, coupling/cohesion, build-time impact).
6. **Content-architecture evolution.** As documented in Section 3, today's localization strategy hard-forks entire sections of markup per culture (`_hu-HU`/`_en-US` Razor partials). This does not scale once content is authored dynamically through the new CMS (#56–#58). Designing how database-sourced, single-source Markdown articles coexist with — and eventually reduce — the current static, duplicated content is a genuine information-architecture and i18n research question directly created by, and answerable within, this thesis.
7. **Client-side performance under growth.** Blazor WebAssembly cold-start size and time-to-interactive are active, well-documented concerns in the wider literature; adding an entire second admin SPA, a REST-based data-access layer, and a JS-interop-driven WYSIWYG editor (#51–#53) is a natural trigger for a rigorous before/after performance benchmarking study (bundle size, Lighthouse/Core Web Vitals, `BlazorWebAssemblyLoadAllGlobalizationData` footprint) — directly requested as an evaluation axis in the thesis brief.
8. **Testing strategy from zero.** No test project exists in the solution today. Introducing one is itself a scoped research/engineering task: unit tests for existing business rules (e.g., `ApplicantModel.Validate`), integration/contract tests for the new Firestore/Storage REST client (ideally against the Firebase Local Emulator Suite), and component tests (e.g., via bUnit) for the new Admin dashboard — establishing measurable coverage and a repeatable regression safety net where none exists.
9. **DevOps for a dual-deployment static architecture.** Issue #60 requires CI/CD that independently builds and deploys two WebAssembly front-ends (public root domain and a protected `admin.` subdomain) from one repository, including environment-specific configuration and secret handling for the Firebase project credentials.

## 6. Expected Outcomes & Deliverables

- **A production-deployed, multi-module system**: the existing public marketing site preserved and extended, plus a new, authenticated Admin CMS, independently built and deployed to two Netlify targets — used in production by a real sports club, not a simulated environment.
- **A reusable Firestore/Storage REST client library** for .NET/Blazor WebAssembly — a concrete engineering artifact with value beyond this single project, given the current absence of an official Firebase SDK for this platform.
- **Technical documentation**: architecture and module-dependency diagrams, the security-rule design and its rationale, and an API reference for the Infrastructure layer's REST client.
- **An automated test suite** covering business-rule unit tests, Firestore/Storage integration (contract) tests, and Admin UI component tests — introducing measurable, repeatable quality assurance where none currently exists.
- **An empirical evaluation chapter**, including quantified before/after client-side performance measurements (bundle size, time-to-interactive, Core Web Vitals) for the WebAssembly application, a documented threat model and mitigations for the authentication and Markdown-rendering pipelines, and a small usability evaluation conducted with the club's actual, non-technical administrators authoring and publishing a real article end-to-end.
- **A written BSc thesis** that situates this engineering work within the relevant literature on serverless/Backend-as-a-Service client architectures, Blazor WebAssembly performance, secure client-side authentication patterns, and content-management system design — and that reflects critically on the trade-offs made, including how the platform's evolving content model resolves the localization/content-duplication limitation identified in the current codebase.
